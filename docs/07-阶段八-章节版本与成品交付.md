# 灵墨（Lingmo）— 阶段八：章节版本与成品交付

> **文档状态：设计已定稿，待施工** — 本文定义阶段八的实现边界、数据结构、接口、交互与验收标准。阶段零～七已验收通过；阶段八尚未实现，不得提前标记完成。

阶段八选择原路线图的方向 C。先补齐章节修改的安全回退能力，再完成 F9 的成品导出与交付检查。方向 B「对话即操作中枢」继续后置；在版本安全底座落地前，不扩张聊天侧的写作动作。

## 1. 背景与目标

当前写作主链路已经可以新建、连续生成、续写、改写、手工保存、定稿和删除章节，但存在四个交付缺口：

1. 手工保存、续写和直接改写会覆盖当前正文，没有历史版本可回退。
2. 导出仅支持整本 Markdown / TXT，且只导出已定稿章节；不能按卷或选中章节导出，也没有 DOCX。
3. 写作页已有当前章和全书字数，但没有独立的全书目录与状态统计视图。
4. 导出前不会集中提示草稿、未闭合伏笔或规则一致性冲突。

本阶段目标：

- 任何覆盖既有作者内容的操作都先原子保存旧版本，作者可查看并恢复。
- 支持整本、按卷、选中章节导出 Markdown / TXT / DOCX。
- 提供与正文一致的目录、字数和状态统计。
- 导出前提供零额外模型调用的风险清单。

## 2. 已核对的现有写入路径

| 写入入口 | 现有落库位置 | 阶段八处理 |
|----------|--------------|------------|
| 手工保存 | `PUT /novels/{novel_id}/chapters/{chapter_id}` → `ChapterRepo.update` | 作者字段实际变化时，覆盖前快照，来源 `manual_save` |
| 改写预览后应用 | 前端 `applyPreview` 调同一个 PUT | 请求显式传来源 `rewrite_apply`，覆盖前快照 |
| 续写本章 | `writing.continue_chapter` → `ChapterRepo.update(content=...)` | 追加正文前快照，来源 `continue` |
| 直接改写（兼容路径） | `writing.rewrite_passage(preview=False)` | 替换正文前快照，来源 `rewrite` |
| 写新章 / 生成下一章 | `writing.write_chapter` → `ChapterRepo.create` | 新建而非覆盖，不生成历史快照 |
| 自动驾驶生成 | `auto_pilot.run_autopilot` → `ChapterRepo.create` | 新建而非覆盖，不生成历史快照 |
| 定稿沉淀 | 更新 `status`、`summary`、`drift_score` 并写章节记忆 | 不生成版本；这些是派生状态，不是作者正文修改 |
| 张力/漂移评分 | 只更新分数 | 不生成版本 |
| 删除章节 | `ChapterRepo.delete`，同时清理章节记忆并解除伏笔引用 | 仍为显式永久删除；同步删除该章版本，不在本阶段实现回收站 |

只有 `title`、`content`、`directive` 三个作者可编辑字段发生实际变化时才创建快照。仅更新 `status`、`summary`、`outline_node_id`、`tension_score` 或 `drift_score` 不得制造版本噪声；相同内容的重复保存也不得产生快照。

## 3. 核心决策

| 决策 | 结论 |
|------|------|
| D1 快照时机 | 覆盖既有作者字段前保存旧状态；快照与更新必须在同一个数据库事务中提交 |
| D2 版本范围 | 保存标题、正文、章前指令及当时的状态/摘要/质量分，供审阅；恢复时只恢复标题、正文和章前指令 |
| D3 恢复语义 | 恢复后强制回到 `draft`，清空 `summary`、`tension_score`、`drift_score`，删除该章旧 `memory_chunk`；作者需重新定稿沉淀 |
| D4 Story Bible | 恢复章节不会反向删除或回滚已经确认落库的人物、时间线、伏笔等 Story Bible 数据；界面必须明确提示 |
| D5 版本保留 | 初期不自动裁剪版本，避免静默丢历史；同内容不重复建版本 |
| D6 删除边界 | 删除章节会同时删除它的历史版本，仍不可恢复；本阶段不引入软删除或回收站 |
| D7 导出范围 | 支持整本、按卷、选中章节；默认仅包含已定稿章节，可由作者显式勾选包含草稿 |
| D8 导出前检查 | 只做可验证的数据库状态与规则层检查，不调用 LLM，不声称识别“未处理的语义冲突” |
| D9 DOCX 实现 | 使用 `python-docx`，作为阶段八唯一新增依赖；不手写 OOXML |

恢复前也要保存当前状态，来源记为 `restore`。因此作者恢复旧版本后，仍可通过新生成的快照回到恢复前的内容。

## 4. 数据模型

新增一张表 `chapter_revision`：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | `VARCHAR(36)` PK | UUID |
| `novel_id` | `VARCHAR(36)` INDEX | 作品 ID，用于严格作用域校验和作品删除清理 |
| `chapter_id` | `VARCHAR(36)` INDEX | 章节 ID |
| `revision_no` | `INTEGER` | 章节内递增序号，从 1 开始 |
| `source` | `VARCHAR(32)` | `manual_save` / `rewrite_apply` / `continue` / `rewrite` / `restore` |
| `title` | `VARCHAR(200)` | 覆盖前标题 |
| `content` | `TEXT` | 覆盖前正文 |
| `directive` | `TEXT` | 覆盖前章前指令 |
| `status` | `VARCHAR(20)` | 当时章节状态，仅供审阅 |
| `summary` | `TEXT` | 当时摘要，仅供审阅 |
| `tension_score` | `FLOAT NULL` | 当时张力分，仅供审阅 |
| `drift_score` | `FLOAT NULL` | 当时漂移分，仅供审阅 |
| `word_count` | `INTEGER` | 去除空白后的字符数，与前端现有口径一致 |
| `created_at` | `VARCHAR(40)` | UTC ISO 时间 |

约束与索引：

- `UNIQUE(chapter_id, revision_no)`，避免同章序号重复。
- 索引 `chapter_revision(novel_id, chapter_id, revision_no)`。
- 新表由 `Base.metadata.create_all` 创建；不需要修改 `_ensure_columns`，因为该函数只负责给既有表补列。
- `NovelRepo.delete` 必须显式清理作品下版本；`ChapterRepo.delete` 必须显式清理章节版本，保持现有手工级联风格。

## 5. 后端设计

### 5.1 版本服务

新增：

- `application/revisions.py`：判断作者字段是否变化、原子快照并更新、恢复版本、清理派生数据。
- `ChapterRevisionRepo`：列表、读取、计算下一版本号、创建与清理。

业务层提供两个核心操作：

```python
update_chapter_with_revision(db, novel_id, chapter_id, changes, source)
restore_chapter_revision(db, novel_id, chapter_id, revision_id)
```

要求：

1. 读取当前章节，并严格验证 `novel_id`、`chapter_id`、`revision_id` 同属一条链路。
2. 只比较 `title` / `content` / `directive`，有实际变化才插入旧状态快照。
3. 插入快照、修改章节、必要的记忆清理必须由同一次 `db.commit()` 完成；失败时 `rollback()`。
4. PUT 路由和写作用例不得先各自提交快照，再单独提交正文。
5. 恢复后返回最新 `ChapterRead`；历史快照本身保持不可变。

### 5.2 API

新增版本端点：

| 方法 | 完整路径 | 说明 |
|------|----------|------|
| GET | `/api/v1/novels/{novel_id}/chapters/{chapter_id}/revisions` | 按 `revision_no` 倒序返回元数据，不返回完整正文 |
| GET | `/api/v1/novels/{novel_id}/chapters/{chapter_id}/revisions/{revision_id}` | 返回单个版本完整内容 |
| POST | `/api/v1/novels/{novel_id}/chapters/{chapter_id}/revisions/{revision_id}/restore` | 恢复目标版本；先快照当前状态 |

扩展 `ChapterUpdate`：

- 新增仅用于接口编排的 `revision_source`，允许值 `manual_save` / `rewrite_apply`，默认 `manual_save`。
- 路由在调用更新服务前必须从正文更新字段中移除它，禁止把它传给 ORM。
- 非聊天或旧前端不传该字段时保持现有兼容行为。

新增导出与统计端点：

| 方法 | 完整路径 | 说明 |
|------|----------|------|
| GET | `/api/v1/novels/{novel_id}/book/summary` | 目录与统计：总章数、总字数、草稿/定稿数、各章字数与质量分 |
| POST | `/api/v1/novels/{novel_id}/export/preflight` | 对指定导出范围做草稿、伏笔、规则冲突检查 |
| POST | `/api/v1/novels/{novel_id}/export/file` | 按请求范围返回 Markdown / TXT / DOCX 文件 |

现有 `GET /export/markdown` 和 `GET /export/txt` 保留，继续代表“整本已定稿章节”，避免破坏旧调用。

导出请求：

```json
{
  "format": "markdown|txt|docx",
  "scope": "all|volume|chapters",
  "volume_id": "",
  "chapter_ids": [],
  "include_drafts": false
}
```

校验规则：

- `scope=volume` 必须提供属于该作品且 `level=volume` 的 `volume_id`。
- `scope=chapters` 必须提供至少一个属于该作品的章节 ID。
- 所有导出结果按 `chapter.seq` 升序，不按前端传入顺序。
- 章节通过 `outline_node_id` 沿父链归卷；未绑定大纲的章节不属于任何卷，但仍属于整本范围。
- 范围内没有可导出章节时返回 400，不生成空文件。

### 5.3 导出前检查

响应至少包含：

```json
{
  "chapter_count": 12,
  "word_count": 35678,
  "draft_chapters": [],
  "unbound_chapters": [],
  "unresolved_foreshadowings": [],
  "rule_conflicts": [],
  "ready": true
}
```

- `draft_chapters`：所选范围内的草稿。
- `unbound_chapters`：按卷导出时不可归入卷的章节仅作全书级提示。
- `unresolved_foreshadowings`：所选作品中状态不是 `consumed` 的伏笔。
- `rule_conflicts`：对所选章节逐章运行现有 `consistency_check`，记录章节 ID、序号与冲突内容。
- `ready` 仅表示没有草稿和规则冲突；未闭合伏笔是警告，不强制阻止导出。
- 不自动运行 `deep_check`，避免一次导出前检查产生最多每章 8 次模型调用。

### 5.4 DOCX

- 新增依赖 `python-docx`。
- 文档标题使用作品名；章节标题使用 Heading 1；章间分页。
- 正文按空行拆段，保留段落，不把整章塞进一个段落。
- 返回正确的 DOCX MIME 类型与 UTF-8 文件名。
- Markdown / TXT 延续当前标题格式，统一复用同一个范围筛选函数，禁止三套筛选逻辑各写一遍。

## 6. 前端设计

### 6.1 写作页版本入口

在写作工具栏增加“版本历史”，选中章节后可用。打开侧边抽屉或宽模态框：

- 顶部显示“当前版本”及当前字数。
- 历史列表显示版本号、来源中文标签、时间、字数和相对当前版本的字数变化。
- 点击版本后并排显示历史内容与当前内容；第一版不做字符级 diff，不新增前端依赖。
- “恢复此版本”二次确认，明确说明：恢复后章节回到草稿，需重新定稿；不会回滚已确认进入 Story Bible 的设定。
- 恢复成功后重新载入章节、清空质量高亮，并把恢复后的内容设为已保存状态。

`applyPreview` 调用 `updateChapter` 时传 `revision_source: "rewrite_apply"`；普通保存传 `manual_save`。

### 6.2 全书统计与导出

新增 `BookDeliveryPanel.vue`，作为工作台独立 Tab“成品交付”：

- 概览卡：总章数、总字数、草稿数、定稿数。
- 目录表：序号、标题、所属卷、状态、字数、张力分、漂移分。
- 导出范围：整本 / 按卷 / 选中章节。
- “包含草稿”默认关闭。
- 先点“导出前检查”，展示草稿、未闭合伏笔和规则冲突；作者确认后再下载。
- DOCX、Markdown、TXT 使用同一份范围选择状态。

写作页原有快捷“导出 MD / 导出 TXT”可以保留，继续执行整本已定稿章节导出；复杂导出统一进入“成品交付”。

## 9. 验收标准

1. 手工保存、改写应用、续写和兼容的直接改写在覆盖正文前各新增一条旧状态快照；无变化保存不新增。
2. 新建章节、自动驾驶生成、定稿、张力评分、漂移评分和仅修改 `outline_node_id` 不产生快照。
3. 版本列表不返回完整正文；读取单个版本才返回正文，且跨作品/跨章节访问被拒绝。
4. 恢复任一版本前会先保存当前状态；恢复后标题、正文、章前指令正确，状态为草稿，摘要与质量分清空，旧章节记忆被删除。
5. 恢复不会自动修改 Story Bible；前端明确展示这一边界。
6. 删除章节和删除作品时不残留孤立版本。
7. 全书与逐章字数使用“去除所有空白字符”的统一口径，前后端统计一致。
8. 整本、按卷、选中章节三种范围的 Markdown / TXT / DOCX 内容和顺序正确；默认排除草稿，显式选择后可包含。
9. 导出前检查能报告草稿、未闭合伏笔和规则层冲突，不调用 LLM。
10. 原有 68 项后端测试不得减少，新增测试后全部通过；前端 `npm.cmd run build` 通过。
11. 浏览器完成版本查看、恢复、三种范围选择、预检查和三种格式下载的人工验收。
12. 不修改真实用户数据，不提交数据库、DOCX 产物、缓存、日志或密钥。

## 10. 明确不做

- 不做章节删除回收站或软删除。
- 不回滚 Story Bible、伏笔状态、对话或大纲结构。
- 不做多人协作、版本分支、合并或冲突解决。
- 不做字符级可视化 diff，不新增前端 diff 依赖。
- 不自动运行语义深度检查。
- 不开始方向 B「对话即操作中枢」。
- 不让 DeepSeek、Codex CLI 或其他开发 Agent 执行任何 Git 写操作。

## 11. 风险

- 全文快照会增加 SQLite 体积；阶段八优先保证不丢稿，不做静默裁剪，后续根据真实使用量再设计显式清理。
- 恢复正文但不回滚 Story Bible 可能留下语义差异，因此恢复后强制退回草稿并要求重新定稿。
- 章节删除仍不可恢复；删除确认框必须继续明确提示，并说明历史版本也会删除。
- 规则层检查能力有限；导出前检查不得把“规则层无冲突”表述成“全文语义完全一致”。
