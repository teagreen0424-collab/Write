# 灵墨（Lingmo）— 方向 B：对话即操作中枢（设计草案）

> **文档状态：设计草案，两项关键方案已由项目管理者裁决；尚未施工。** 阶段八已由项目管理者于 2026-09-23 验收通过。本文把路线图方向 B 转成可施工、可验收的方案；除第 8 节明确裁决的两项外，其余细节仍属设计草案，不代表已实现。

## 1. 目标与不可突破的边界

让作者在绑定作品的聊天中，把讨论结论变成大纲、章节草稿或设定卡，并让旧章节细节可被相关讨论召回。核心仍是“**讨论零写入，预览零写入，作者确认才落地**”。全局会话先“转为作品”或“移动到作品”，不能静默选择作品。Story Bible 仍是设定事实源；召回文本是历史证据，不得覆盖当前设定。聊天写章只建草稿，不自动定稿沉淀、不自动驾驶、不改已有章节。沿用现有 LLM、嵌入与向量组件，不新增依赖。

## 2. 现状盘点与设计差距（已按代码核对）

| 能力 | 当前代码 | 差距 |
|------|----------|------|
| 对话流 | `application/chat.py` 存 user、流式回复、存 assistant；仅绑定作品时附带轻量人物/世界观/大纲/最近摘要 | 未调用语义召回；`build_chat_context` 超预算时整节丢弃，极端情况下人物节也可能全部丢失 |
| 聊天设定落地 | `MessageBubble.vue` → `ApplySuggestionCard.vue` → `ideaChat`/`ideaApply`，传实际 assistant 正文并写 `injection(channel=chat)` | 已有可编辑建议，但不限定“人物/世界观/伏笔”的提炼视图；`message.meta` 的 PATCH 是整值替换，新增动作会互相覆盖 |
| 大纲 | `OutlinePanel.vue` 与 `api/v1/outline.py` 只有卷/幕/章的手工 CRUD 和同级重排 | **没有 AI 大纲生成用例可复用**。须先建共享“规划预览→确认写入”用例，再让聊天和工作台共同调用 |
| 写章 | `application/writing.py::write_chapter` 接受指令、标题、`outline_node_id`、`previous_chapter_id`，流式生成并保存草稿 | 可复用写章核心，但聊天需要来源校验、确认表单、动作结果与跳转；提交事务要与动作留痕协调 |
| 记忆 | `memory.py` 只在定稿时写章节切片；`vector.search` 查本作品全部 `memory_chunk`；`context.py` 已在写章时召回 | 设定实体没有索引与更新/删除同步；旧描述一旦被嵌入，会在后续检索中残留 |
| 设定写入口 | 通用 CRUD、`inject_idea.py::apply_injections`、`settle.py::apply_suggestions` 都会写实体 | 只改前端或一条 API 会漏索引同步，必须共用写入/索引服务或覆盖全部入口 |

## 3. 用户流程与交互建议

### 3.1 消息动作

仅持久化完成的 assistant 消息展示“提炼设定”“生成大纲”“写这一章”；全局会话展示禁用态与“先绑定作品”。消息正文是动作来源，不把聊天历史自动写成事实。用户可对同一条消息分别执行不同动作；已完成的动作展示结果摘要与“去设定/去大纲/去章节”入口。换会话或刷新后仍可读到结果。若目标后来被删除，跳转入口显示“目标已删除”，不指向错误作品。

“提炼设定”复用现有 `inject_idea` 的解析、匹配、编辑、确认机制，首版只展示人物、世界观、伏笔三类草稿。解析结果必须可逐条编辑/取消，不可因打开卡片而写库；确认时沿用 `apply_injections` 的既有设定变更、未生成大纲重规划与一致性检查行为，并只写**一条**对应 assistant 原文的 `injection(channel=chat)`。卡片须提示确认可能调整未生成大纲。原“应用到作品”六类建议入口保持兼容，不叠加调用两次 `ideas/apply`。

“生成大纲”先根据消息和当前 Story Bible 输出可编辑的卷/幕/章树**预览**。作者可修改标题、概要与层级；确认后追加到本作品大纲，不替换已有节点。首版建议每次确认创建一卷及其子节点，避免隐式覆盖已有规划。成功后显示新增节点数量和进入大纲页的入口。错误或取消不产生节点。

“写这一章”显示标题、章前指令、可选章级大纲节点，以及“承接当前最新章”的默认选项；作者确认后调用现有写章核心，流式显示进度，落库为新草稿。承接时复用现有“只能从最新章续写”的验证；若期间最新章已变化，拒绝并要求重新确认，不生成脱节章节。完成后显示新章标题和进入写作页入口。生成失败不留半章。

### 3.2 从聊天跳工作台

当前 `App.vue` 只保存 `view` 与 `workbenchNovelId`，没有指定 tab/实体的导航能力。施工时增补跨视图导航参数（作品 ID、tab、可选节点/章节 ID），`WorkbenchView.vue`/子面板接收并选中目标；不引入路由依赖。跳转始终核对结果所属作品。

## 4. 后端与接口草案

现有 `/api/v1` 前缀不变。所有消息动作先查：会话存在、已绑定作品、消息属于该会话且 `role=assistant`、目标实体属于同一作品。错误明确区分未绑定、来源错误、旧目标已删除与重复执行。

| 方法 | 完整路径 | 作用与副作用 |
|------|----------|--------------|
| POST | `/api/v1/conversations/{conversation_id}/messages/{message_id}/settings/preview` | 复用解析用例，返回人物/世界观/伏笔建议；只读数据库，调用模型一次 |
| POST | `/api/v1/conversations/{conversation_id}/messages/{message_id}/settings/apply` | 接收经编辑的建议，复用 `apply_injections`；确认写 Story Bible 与一条 chat injection，返回实体 ID |
| POST | `/api/v1/conversations/{conversation_id}/messages/{message_id}/outline/preview` | 调共享大纲规划用例，返回有层级且可编辑的预览；不写大纲 |
| POST | `/api/v1/conversations/{conversation_id}/messages/{message_id}/outline/apply` | 校验预览结构后原子追加大纲节点，返回卷与子节点 ID |
| POST | `/api/v1/conversations/{conversation_id}/messages/{message_id}/chapter/write` | SSE：`token` / `done`（含 chapter）/ `error`；确认后复用写章用例并落草稿 |
| GET | `/api/v1/conversations/{conversation_id}/messages/{message_id}/actions` | 读取各类已完成动作的结果摘要与目标 ID，供刷新后回显 |
| POST | `/api/v1/novels/{novel_id}/outline/preview` | 工作台调用同一个规划用例，不依赖会话 |
| POST | `/api/v1/novels/{novel_id}/outline/apply` | 工作台调用同一个确认写入用例；不维护第二套大纲生成逻辑 |

上述 API 是**建议接口**，非现有接口。大纲规划须使用集中管理的 Prompt、显式 JSON schema 校验和卷→幕→章父链校验；不相信模型输出的 ID、`novel_id` 或任意操作指令。写章请求复用 `WriteChapterRequest` 语义，不让 assistant 文本直接成为不可编辑的最终指令。`/outline/apply` 不重新调用模型，失败全回滚。不能只循环调用当前逐次 `commit` 的 `OutlineRepo.create`；需拆出可在单事务内批量写入的共享应用用例。

**重复提交与动作记录（已裁决）**：增设 `chat_action` 小表，按 `message_id + action_type` 唯一约束（一条消息每种落地动作首版最多一次），保存动作状态、来源作品、结果 ID/摘要与创建时间。一次动作的实体写入与完成记录同事务提交，断线重试返回原结果而不再写实体/章节；预览不建动作记录。`message.meta` 只保留兼容既有 `applied` 的用途，不再作为新动作的唯一幂等依据；既有 `PATCH` 全量替换问题需改为合并更新，避免旧状态丢失。写章流式输出结束后的“建章+记录动作”须共用一次提交，不可先建章再独立记动作。`apply_injections` 当前逐实体提交，接入动作时须抽出事务可控的共享写入核心，不能简单包装原调用后宣称原子。并发点击由唯一约束与服务端状态检查兜底，前端按钮锁只是附加保护。此项涉及**新增一张表**；列与迁移方式在施工设计中细化。

## 5. 对话语义召回与设定索引

### 5.1 上下文装配

仅绑定作品的会话，用当前**用户消息**作语义查询，调用阶段五的本地 `vector.search`，取最多 3 条相关片段（建议参数）。顺序建议：当前人物卡/直接 Story Bible 设定 → 召回片段 → 世界观/大纲 → 近期摘要；召回内容标记来源（章节历史或设定索引）及“历史片段非当前设定”。按每段截断、总预算裁剪，不整节抛弃优先级最高的人物卡；相同文本去重。检索/嵌入失败降级为无召回，不阻断聊天。全局会话不查任意作品。历史消息条数与上下文预算要分别控制，不让召回挤掉最新用户提问。

### 5.2 实体变更后的索引同步

推荐复用 `memory_chunk`，每个设定实体一条当前索引：`kind=setting`、`embedding_id=实体 UUID`、`source_chapter_id=""`；`embedding_id` 现有字段长度为 36，正好容纳 UUID，无需对该表加列。文本由实体类型、名称及当前有效字段规范序列化；关系类 ID 应解析成当前名称。创建/更新时替换同一作品同一实体的旧块，删除时清除；检索时排除失效块，并始终以实时 Story Bible 为准。实施前需逐一覆盖通用 CRUD、`ideas/apply`、定稿建议确认以及其他实际写入口，而不是只给聊天落地加钩子。

既有作品需要**显式、幂等的存量索引重建**（建议作品设置里提供“重建设定索引”及进度，不在每次启动时隐式全量嵌入）。重建只处理设定块，不删除章节切片。嵌入失败时实体写入仍成功，但旧设定块必须被清除或标为不可检索，不能让旧描述继续被检索；界面提示“索引待重建”。索引与实体写入的事务边界应保证旧块不在更新提交后继续可见。章节历史片段可能记载旧事实，应标注为历史，不作为当前设定结论。

## 6. 施工顺序（建议分两轮）

1. 明确并实现动作记录/事务边界与跨视图跳转协议，给已有 `message.meta` 留痕做兼容回归测试。
2. 设定提炼：复用 `inject_idea`，限制三类预览、逐条编辑、确认一次落库和一次 injection；保留旧“应用到作品”。
3. 新建共享 AI 大纲预览与原子应用用例；先供工作台使用，再接聊天动作，补树结构、失败回滚和重复提交测试。
4. 复用写章核心接聊天 SSE，补“承接最新章”的并发检查、动作结果与跳转；不得自动定稿。
5. 把语义召回接到绑定作品的聊天，重做字符预算与来源标签；全局会话保持无作品上下文。
6. 建设设定索引同步与显式存量重建，覆盖所有设定写入口与失败降级；用旧描述更新案例验收。
7. 两轮分别跑全量后端测试、前端构建/类型检查；在**隔离数据库**做浏览器端到端验收，再更新状态文档。真实用户数据库不用于破坏性测试。

## 7. 拟验收标准

1. 全局会话不能直接执行作品动作；绑定作品后，选定 assistant 消息可以预览，预览、取消和普通聊天不修改大纲/章节/设定。
2. 提炼设定草稿可逐条编辑/取消；确认后写所选人物/世界观/伏笔与**一条** `channel=chat`、正文等于来源消息的 injection；既有未生成大纲重规划与一致性检查行为不回归，卡片事先提示可能调整大纲；原“应用到作品”六类能力无回归。
3. AI 大纲先预览，确认后卷/幕/章层级、顺序与归属正确；工作台立即可见。已有大纲不被覆盖；失败不留半棵树；断线重试不重复创建。
4. 聊天写章遵循已选大纲节点、作者指令和最新章节前情，仅生成一章草稿；成功可跳转，失败或重复确认不多写章。
5. 已完成动作刷新后能显示结果；多个动作并存不互相覆盖；来源消息、会话、作品不匹配时拒绝。
6. 绑定作品的对话提问能召回相关旧章节片段并显示来源；检索故障可正常回复；全局会话不召回任何作品数据。
7. 修改人物设定后，**设定索引**召回的是新描述而非旧索引；删除实体不残留其设定块。既有作品重建后可检索；章节历史文本与当前设定明确区分。
8. 无新增依赖；原有 109 项后端测试不得减少，新增测试全部通过；前端 `npm.cmd run build` 与类型检查通过；浏览器在隔离数据库验证关键交互。

## 8. 项目管理者裁决（2026-09-23）

1. **接受新增 `chat_action` 表**：以数据库唯一约束和同事务提交保障聊天动作可重试、不重复落库；不能只靠前端按钮禁用。
2. **AI 大纲首版每次预览一卷**：作者确认后只追加到现有大纲，不覆盖已有节点。
