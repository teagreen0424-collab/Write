## 第四阶段发现

1. 写作页的正文编辑器只在已选现有章节时出现，保存也只更新已有章节；空作品必须先依赖模型生成，无法完成 PRD 的人工主导写作与离线本地写入。后端已有章节创建接口，可补齐前端闭环，不需要新增外部依赖。
2. 普通手工正文修改仍沿用已定稿状态、旧摘要和评分，摘要链优先使用这些旧摘要，默认交付也可能包含尚未重新审校的新正文。此前阶段八明确了恢复失效；本阶段补齐普通修改后的失效语义，保留修改前快照及单独摘要/状态编辑的既有合同。
3. 普通保存会用迟到返回覆盖等待期间的新编辑；定稿和整章修订已有来源保护，其他当前章检查还需同样核对真实来源。
4. 临时 SQLite 中两个线程同时保存时，版本编号均以 `max+1` 计算，一条保存会触发唯一约束错误。另已用真实续写用例复现：模型等待期间另一请求保存的新稿被旧续写结果覆盖，版本快照也来自旧 ORM 缓存，没有保留那份新稿。本阶段在实际写入时局部串行化、重新读取并核对来源，不在等待模型期间占用写锁。

以上条目先复现再补回归，不因前三阶段技术复核通过而忽略新阶段的实际缺口。

## 第四阶段实现与复核（2026-10-07）

- 空作品及“新章”直接显示手写编辑器，显式保存调用现有章节创建接口，默认草稿，无模型调用。保存冻结作品、章节、编辑器生命周期与作者字段；等待期间的新编辑保留为未保存文本。新建成功后先记住章 ID，后置目录刷新失败不导致重复新建。
- 标题、正文或章前指令实际变化时，同一事务保存真实覆盖前稿件，并让旧定稿、摘要、张力、漂移及该章记忆失效。单独校正摘要或状态不制造作者版本；其他作品、章、大纲绑定与 Story Bible 保持不变。
- SQLite 写锁只覆盖重读、版本号分配与实际写入，模型等待期间不占写锁。续写和直接改写在实际写前核对作者源字段，发现另一请求改稿时拒绝覆盖并保留生成输出。并发手工保存保留顺序和真正被覆盖的正文。
- 四类当前章检查、普通保存、删除、摘要、改写确认、版本恢复和目录读取补齐异步来源保护；作品/章节离开再返回、正文改动再改回及卸载也会让旧回应失效。版本窗口内部的目录、详情和恢复独立保护来源；恢复成功先同步正文，目录刷新失败只报告后置故障。
- 独立真实 SQLite 复核发现并修复两个边界：已 `flush` 的 ORM/Core 未提交写入不能因章节短锁而被回滚；提交成功后响应不用再查库，另一连接的排他锁不能把实际成功误报为 409。六个原故障场景按同一方式复验通过。

## 第五阶段评估输入

已用仓库外临时 SQLite 测量 500 设定节点、500 关系、100 章×6000 字，嵌入使用 384 维固定假向量，无外部模型调用。普通 CRUD 的 P95 约 13～21ms；高关联人物有 100 条边时，仅修改目标仍调用 101 次嵌入并执行 606 条 SQL，模型零成本条件下 P50 398ms、P95 419ms，改名 P95 439ms。模拟每次嵌入 2ms 时，后者升至 672ms。

这些数字用于定位重复关系索引工作，不代表真实本地模型延迟或所有机器的性能承诺。第四阶段验证后，优先减少名称未变时的关系索引刷新，并评估批量构造名称和替换索引；保持现有索引与 Story Bible 同步及失败失效的安全语义。

同一作品的全章节列表传输约 1.897MB，单章约 19KB，六类图谱数据约 1.061MB。本轮先处理已定位的重复索引与初始资源问题，章节目录元数据投影作为后续评估输入，保持现有完整章节及导出接口兼容。

生产构建内存测量中，现有初始 JavaScript 为 1,770,981 字节（gzip 561,071）。临时按需加载工作台及七类面板的实验可降到约 503,977 字节（gzip 153,561）；ECharts 仅导入实际图表与组件后，总 JavaScript 可减少约 28%。这是隔离实验，尚未作为已实现结果。第五阶段实现必须保留设定面板首次访问后隐藏时的编辑状态、图谱跳转和现有导航保护，不能以丢失作者输入换取资源减少。

## 第六阶段评估输入

六个临时 SQLite 场景证实：同稿两次提炼并确认时，人物、时间线和伏笔各从 1 条变成 2 条；部分成功的回应丢失后重发整批，原成功人物重复；两个并发确认各创建一份；另一请求已改稿并让章节回到草稿后，旧建议仍能返回成功并写入 Story Bible。直接手工 CRUD 创建两个同名不同人物是合法行为，按名引用则明确报歧义，不能为去重而破坏这一合同。

第五阶段通过后，优先实现同一作者稿与规范化建议的持久逐项确认记录，实体、当前索引及记录同一事务提交；成功项重试返回原结果，来源变化拒绝旧建议，并保留已提交部分的真实结果。新表迁移须幂等，删除章节/作品清理相应记录，已删除实体不能因旧请求重试而静默复活。
